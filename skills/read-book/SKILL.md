# Read Book

把一本中文书或中文译本整理成渐进式阅读地图：先建立全书结构，再按真实问题深挖，最后回到原文。忠实呈现作者观点，同时把报告综合、批判审计和外部资料明确分开。

## 固定边界

- 每次任务只使用一个 `OUTPUT_ROOT` 作为生成物事实源。
- 优先使用用户明确指定的读书地图仓库；未指定时，从当前仓库或解析符号链接后的 Skill 真实路径定位包含 `books/` 的根目录。无法唯一定位时先询问，不自行创建第二份。
- 把书籍产物写入 `books/<中文书名>/reading.html` 与 `reading.json`。
- 把深挖模块写入该书的 `modules/<module-slug>/reading.html` 与 `reading.json`。
- 只读取用户提供的私有原书；原书目录保持只读，不在原书旁写入 HTML、JSON 或模块。
- 不复制、提交、推送、发布或公开 EPUB、TXT、PDF 等原书。未经明确授权，也不要提交、推送或发布阅读地图。
- 用户说“分析”“审计”“先不改”“等我确认”时保持只读；用户明确要求“生成”“修订”时才写入。
- V1 支持中文内容的 TXT、Markdown 和 EPUB；PDF 暂不支持。

## 选择模式

1. **主地图**：书目录下没有 `reading.json`，或用户明确要求建立全书模型。
2. **深挖模块**：已有主地图，用户对具体篇章、主题、人物、概念或历史问题提出进一步兴趣。
3. **最小修订**：用户要求审计、精简或修正现有地图。保留有效结构，只改真实问题。

不要为主地图和深挖拆分另一套 Skill。它们共享来源审计、观点标型、产物结构和验证规则。

## 执行流程

### 1. 核对意图和现状

- 读取用户请求、原书路径、已有 `reading.json`、主页面和相关模块。
- 先区分用户目标、写入授权和候选做法。不要把“看看”当成生成授权。
- 检查同名书目录，避免覆盖既有人工修订。需要改动时先说明实际范围。

### 2. 审计原书

- 计算来源文件的 SHA-256、字节数和可核对的结构统计。
- TXT：识别编码、正文范围、异常空白、广告和拼接污染；保留行号定位。
- Markdown：保留标题层级与段落定位，检查缺章和异常附加内容。
- EPUB：验证 ZIP、container、package、spine、目录和正文文件；记录内部文件定位。只在临时目录解包，完成后清理。
- 冻结纳入与排除范围。缺少出版社、译者、ISBN、印次或版次时如实说明，不补造元数据。
- 若版本冲突会改变理解，停车说明；若只影响旁支背景，保留差异并继续。

### 3. 建立可核证模型

- 先做限时检视：阅读书名、目录、序言、结尾和关键段，判断书类、全书问题、结构与是否值得继续；不要先逐章摘要。
- 让模型回答四个主动问题：全书说什么；各部分怎样展开；主张或论证是否成立；对读者的判断或行动有什么意义。
- 需要分析时按“结构—诠释—批评”推进：先重构整体与部分，再对齐术语、主张和论证，最后用知识、事实或逻辑评价。没有准确理解前不要反驳。
- 按书类调整重心：实用书关注目标与行动，历史关注叙述与证据，思想或理论书关注概念与论证，文学作品不强套论证模板。
- 在检视结果上补出关键概念、主要人物或力量关系，以及作者的核心论证。
- 逐条区分：`作者原话`、`作者主张`、`报告综合`、`批判审计`、`外部背景`。
- 直接摘录必须逐字核对并附卷次、篇名、章节、行号或 EPUB 内部路径。只摘录理解关键论证所需的短段，不堆砌名句。
- 不用后见资料替作者发言。外部资料只用于背景、版本或历史压力测试，并明确来源。
- 用户未禁止时，可联网核对背景和版本；优先权威或一手来源。网络材料不能替代用户提供的原书。

### 4. 生成渐进阅读路径

- 主页面控制在约 30–45 分钟可读完，帮助读者掌握背景、结构、思想、人物或力量关系、主要观点和是否值得细读。
- 推荐少量原文锚点，使第一轮总阅读量通常可在 1–2 天的业余时间完成。
- 深挖模块控制在约 45–90 分钟，只回答用户已经表现出的一个问题；不要预生成百科式模块。
- 每个深挖都给出回原文路线，并说明它不是原书新增章节。
- 模块生成后再更新主页面入口和 `reading.json`；二级模块必须标明父模块。

详细字段、页面结构和标型规则见 [产物契约](references/artifact-contract.md)。

### 5. 按需使用图

- 只有当图能明显降低理解成本时才画图，例如同时存在三组以上关系、阶段、层级、因果或反馈。
- 一张图只表达一个中心问题。先提取节点、关系和方向，再选择时间轴、流程图、关系图或结构图。
- 使用短标签和明确箭头语义；两种以上箭头含义时给出图例。不要让箭头穿过节点、标题或正文。
- 不画无法从来源核实的人物场景、氛围插画或装饰性“证据”。不要为了视觉丰富重复正文已经讲清的内容。
- SVG 保持离线、自包含、可缩放和移动端可读。自动检查 XML、引用和几何后，还要目视检查文字、箭头、留白和滚动行为。
- 若宿主已有 Fireworks、UI 或设计审计能力，可以把它们用于增强和独立复核；不可把这些宿主特有 Skill 设为硬依赖。

### 6. 写入产物

- Markdown 或分析过程不是发布真源；稳定产物是自包含 `reading.html` 加结构化 `reading.json`。
- HTML 使用语义化标题、清楚导航、可见焦点、足够字号、减少动态效果和无脚本可读结构。
- 保持现有书籍页面的视觉语言。新增模块应复用该书的颜色、排版、证据标签和导航，不另起一套风格。
- 新增书籍时按需更新仓库首页和 README；只新增深挖时通常只更新该书主页面和 JSON。

### 7. 验证和复审

生成或修订后运行：

`<SKILL_DIR>` 是解析符号链接后的本 Skill 目录。

```bash
python3 "<SKILL_DIR>/scripts/validate-reading-map.py" \
  "<OUTPUT_ROOT>/books/<中文书名>"
```

然后执行两阶段复审：

1. **内容复审**：范围、版本、原文定位、引文、作者观点、外部事实和批判边界是否真实。
2. **阅读与 UI 复审**：主线是否能快速读懂；桌面和手机是否溢出；SVG 是否真的比文字更清楚；是否出现重复和过密。

能读取页面图像时，至少检查一个桌面和一个手机视口。不能目视检查时明确标记未验证，不要声称 UI 已通过。

## 结束条件

最终说明：写入了哪些文件、使用了什么来源、哪些验证通过、哪些仍是推断或未验证、下一步应该停止还是回原文。不要把地图描述成已经替用户读完原书。
